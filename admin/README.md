# admin/ — the :7878 panel

Zero-dependency local web panel over the monitor's evidence (`node:http` + siblings only).

```sh
node admin/serve.mjs [port]                     # http://127.0.0.1:7878 (CW_ADMIN_PORT / argv override)
node bin/test-run.mjs 'admin/**/*.test.mjs'     # the panel's own suite — routes, rendering, auth, CRA, docsite (also in `npm test`)
```

The operator port is one higher (`CW_ADMIN_LOCAL_PORT`). Its local name is **`http://commitwork.local`**:
`node bin/panel-local-name.mjs --write` writes an install script for the operator to read and run
with sudo. The script adds a hosts entry, plus a pf rule that sends loopback :80 to the operator port.
`--check` reports which step fails, without root. The name is not a secure context, so the copy
buttons and passkey enrolment need `127.0.0.1`. The panel refuses to boot if the tunnel would reach
loopback :80 (`admin/local-access.mjs`). Quote the glob: `node --test admin/test/`
resolves the directory as a module and fails on Node 26 ([docs/TRAPS.md](../docs/TRAPS.md)).

Binds **loopback only**; the outside world reaches it exclusively through the cloudflared tunnel
(declared per-area in the fleet registry, `monitor/private/projects.json`, fragment generated by
[`bin/deploy.mjs`](../bin/README.md)).

## Navigation components

Every view has one scope, declared in `VIEW_SCOPE` (`menus/navigation.js`): **fleet** views
cover every project and ignore the picker, **project** views (the default) cover the selected
project, and **account** is the operator's own settings. The rail, breadcrumb, header, URLs and
run controls all read that table.

The section rail (`menus/section-rail.html`) has three parts. **All projects** links to the fleet
views: overview, rollups, project list, agent follow-ups, decisions & reviews and reporting
deadlines. **Project** holds the project picker and that project's six workspaces — **Summary,
Findings, Websites & services, Site map, Work and History**; these stay disabled until a project is
chosen. Findings offers all findings, security risks, code quality, accessibility and other checks,
and every scanner-specific page stays reachable through the check selector. **Manage** holds check
schedules, check configuration, credentials & connections, the `/config` page and service
operations (panel health, restart, healthcheck). Narrow windows use an expandable Navigate control.
Account security forms live on the Profile page.

The top bar shows a scope chip (`All projects` or `Project · <name>`), the freshness that matches
it (the newest scan across areas on fleet views, the project's rollup age on project views),
refresh and the account menu. The run control and the healthcheck box appear only on project
views and name the project they run; the server refuses a sweep or healthcheck with no project.
Choosing a project on a fleet view opens its Summary; clearing it on a project view opens the
fleet overview. Fleet and account URLs carry no project segment.

Edit `panel.html` for page content and `menus/` for navigation. The top bar, account menu,
section rail, view selector, account forms, navigation behavior and inline styles have separate
source files. `lib/panel-document.mjs` composes the response from a fixed list of these files;
inline stylesheet blocks receive matching CSP hashes.

The client code lives in `static/panel-*.js`: eight classic scripts (`panel-core`, `panel-console`,
`panel-posture`, `panel-views`, `panel-router`, `panel-features`, `panel-settings`, `panel-boot`),
loaded in the order `panel.html` lists them, after the extracted view modules (`learning.js`,
`comments.js`, `overwatch-layer.js`, `bola.js`, `perf-console.js`) and with `menus/navigation.js`
and `menus/account-menu.js` inlined between them. They share one global scope, and a function
declaration is hoisted only within its own script, so top-level code may call only what an earlier
script declares; `panel-boot.js` stays last. `static/` is an allowlist: a script is served only once
it is named in `STATIC_JS_MODULES` in `serve.mjs`.

After editing, run `node bin/build-admin-panel.mjs` from the repository root. This atomically
rebuilds `index.html`, the complete compatibility entry for already-running server processes
that still read that file directly. Do not put unresolved component markers in the live entry.
The workspace navigation test verifies that the entry matches the component sources.

## Views

Every view belongs to one workspace, and the workspace is DERIVED from the view by `workspaceOf()`
in `menus/navigation.js`, never stored beside it. The rail opens each workspace at its default view.

- **All projects** (fleet scope; the picker does not apply) — Overview (`fleet`) · Rollups ·
  Project list (`projects`) · Agent follow-ups (`overwatch`) · Decisions & reviews (`verdicts`) ·
  Reporting deadlines (`cra`). `oversight`, `stpa`, `bola`, `comments` and `spinecomments` are
  fleet-scoped too and reached by path or from the strip while a fleet page is open.

  **Fleet** (All projects → Overview) is where a bare `/` with no project and a cleared project
  picker land. The project views describe the *selected* project, so the panel's front door used to
  be a page it could not answer: a prompt and four empty tiles. Fleet is box-wide by construction —
  total CVEs and KEVs across every area, how many areas are swept, the sweep deadman's verdict per
  area, and when each last scanned (`GET /api/fleet/overview`, `admin/routes/fleet-overview.mjs`).

  Three properties are load-bearing and are what the tests hold in place. **Every total names its
  denominator**: 39 area directories do not all contribute to every sum — some have never been
  swept, some predate a field, and some never loaded the KEV catalogue — so a figure prints
  *over N of M areas* and the non-contributors are named rather than counted as zeros. **The health
  verdict is the deadman's own**: the route calls `monitor/liveness.mjs`'s `checkOne()`, the same
  function the hourly launchd agent runs, so this page and the alarm cannot disagree, and a state
  added to the deadman later renders here as alarming rather than clean-by-omission.

  **Severity and remedy are separate axes, and the headline uses the second.** `RANK` orders states
  by how bad they are, which is the right input for an exit code and the wrong one for a dashboard:
  measured 2026-09-11 with the nightly wave running, ranking alone said *"27 of 39 areas need
  attention"* — of which 15 had a sweep executing inside them at that moment and wanted no action at
  all, while the 3 whose sweeps had died were the entire actionable content and sat buried in the
  number. So every area also carries a `kind`: **in-flight** (a live sweep pid — progress, excluded
  from the headline and coloured grey, because until it finishes what is on screen is the previous
  slice), **behind** (swept, but not recently or completely enough), **broken** (the sweep or its
  evidence failed), **ok** (fresh, or deliberately quiet). This is the same distinction liveness
  itself drew when it split `overrunning` out of `hung`; the page had re-merged it one layer up, in
  the summary, which is where a reader actually looks. A state absent from the map is classified by
  its rank and fails closed to `broken`.

  The Overview tab's refusal to fill its project-labelled KPI row with a fleet-wide sum is
  **unchanged** — a fleet total is not a project's posture, and that row is labelled with a project.
  What Fleet adds is a page where the same numbers are attributable to the population they came from.
- **Summary** — Overview · Dashboard · Lanes · Posture. Posture answers "which security approaches
  do we run, and are they still running"; Delivery (under Work) is its non-security half (build
  health, release gates, inventory, hygiene). They are separate boards because they answer
  different questions and fail independently — see `monitor/posture.mjs`.
- **Findings** — All findings, then the security risks (secrets, static analysis, dependencies,
  running services), code quality (lint, types, quality) and accessibility pages, and an Other
  checks category that catches any view no `TAB_GROUPS` entry places. Every scanner page, including
  the per-lane tabs and the lane tabs generated from `monitor/lane-tabs.mjs`, is reached through the
  check selector.
- **Websites & services** — Exposure · Vendor.
- **Site map** — Sitemap.
- **Work** — Remediation (the plan) · Issues (each row expands to lodge a **ruling** — is the
  finding real — and a **fix type** — how it was addressed — with the annotation explaining both;
  two dropdowns because they are two questions, and collapsing them is how a suppression gets filed
  as a fix. Both are claims; neither closes) · Daily suggestions (`daily`: the /daily report for the
  project's area, each suggestion with the veld todo it was filed as) · Delivery · Modmap.
- **History** — Report (the evidence) · Timeline.
- **Manage** — Check schedules (`settings`) · Check configuration (`perf`) · Credentials &
  connections (`held`) · Profile.

This list is prose and drifts. `const NATIVE` in `static/panel-router.js` enumerates the native
views, `VALID_VIEWS` beside it adds the iframe views, and `workspaceOf()` decides where each one
appears.

Each tab's explanatory gloss is a `title=` tooltip, not a second label line.

*(Deliberately not "N tabs": the count was written as `Thirteen` and was wrong by nine within a
fortnight, because a number in prose has no test holding it up. `tab-routes.test.mjs` asserts the
nav strip and `VALID_VIEWS` agree, which is the invariant that actually matters.)*

Most tabs carry a **count badge**. The badge is only rendered once a real number is known, and
is *cleared* — not zeroed — when a source is missing, unparseable, or simply not loaded yet: a tab
nobody has scanned must never read the same as a tab that was scanned and came back empty. Runtime,
CodeQL, Modernization and the three scanner-detail tabs ride on the `/api/state` poll the panel
already makes; Exposure, Renovate and Remediation set their own badge when their tab is first
opened, because their sources are lazy (`/api/exposure` actively probes DNS and origins, so polling
it for a badge would mean probing the fleet every 8 seconds).

**Secrets · Malware · Supply chain** are the drill-down behind three scanner-coverage categories
(gitleaks, OSV `MAL-`, GuardDog), rendered from the rollup's `scannerFindings` block passed through
`/api/state` whole — no second producer, no pointer file, no log scraping (deliberately NOT the
CodeQL tab's pipeline). Each states its own coverage
before its rows: **carried** (not re-run by this sweep — rows named with their source slice),
**VOID** (`ran === 0` renders the void instead of an empty table), **partial** (`noscan > 0` — rows
are a floor; GuardDog sits here structurally, being docker-gated), and **truncated** (the rollup
caps detail at `DETAIL_CAP` rows per repo per category — 10,000, set in `monitor/extractors.mjs` — and the banner states the true total, which is never capped).
Secrets rows are whitelisted at the extractor (rule/file/line/commit); no gitleaks `Secret`/`Match`
field exists anywhere in the payload.

**The Remediation tab leads with triage prompts.** The manifests carry per-check
`remediationPrompt` guidance (`security-baseline.json`, `runtime.json`) — written to be copied to
an agent together with that scanner's artifact. The tab renders them from
`GET /api/remediation/prompts`, each joined server-side with the selected project's `scanners`
entry from the same rollup `/api/state` serves, so the pill beside a prompt and the coverage table
cannot disagree. Prompts whose category has live findings float first (severity-weighted, top card
open, one-click copy); clean and no-signal prompts collapse but stay present — a documented
procedure does not stop existing on a clean day. A check outside the fleet scanner categories
(TruffleHog, `tls-headers`, …) shows **no live counts**, never a fabricated zero. The KEV-ranked
`REMEDIATION.md` plan renders below; its count is the plan's own section headings, read server-side
(`planSummary()`), because the plan is tables and a bullet count read 0 for every plan.

Every read resolves through `reportsFor()` for the SELECTED project, and an **Inputs** strip heads
the tab: `rollup.json`, `REMEDIATION.md`, the sweep batch the rollup names (reports-root-relative
since `sourceKey()` — resolved against the reports root, not the panel's cwd), the verified-fix
ledger and `codeql-fleet.json`, each present, missing (with the step that produces it) or
unreadable, plus the layer's own records (`handoff/`, `codeql-remediation/`). No project, an unknown
project and an unresolved one are named states, never a row of absents; a handoff without a
resolved project is refused rather than filed under `reports/__unresolved__/`.

**Remediation · all projects** (`/remfleet/`, rail link under All projects) is the same read for
every declared area plus any undeclared report directory holding a rollup or a plan, sorted by
label then directory: plan packages/findings/KEV, the prompt tally through the tab's own classifier
(`rpWeight`), triage runs, CodeQL findings and runs, verified fixes, and the missing inputs by name.
A never-scanned project is a row naming all five, not a dropped row.

Each prompt card can also **hand off**: *Claude Code ↗* has the server compose a handoff file
(prompt + the scanner artifact's path from the batch the rollup actually rolled + live counts) and
start a `claude` session on it. The launch tries, in order, `CW_HANDOFF_CMD` (split by
`quotedArgv()`, so a quoted path with a space is one argument; no shell; a command that cannot start
is reported, not assumed started), the overwatch-layer runner, and finally VS Code at the target
repo plus a `claude` session in a new Terminal window with the handoff already submitted — there is
no public surface for prefilling the VS Code extension's chat, so the Terminal session is the
realisation, stated as such.
*local LLM ▸* runs the prompt on a local model. The hosts are declared once in
`manifests/llm-hosts.json` (llama.cpp, LM Studio and the other OpenAI-compatible servers; ollama was
removed on 2026-08-27 because it alone needed its own request shape), each URL overridable as
`CW_LLM_URL_<ID>` (`CW_LMSTUDIO_URL` is still honoured), and **nothing is probed until the operator
switches runners on, per host, in Settings** — the targets route reports `disabled`, `none-enabled`
or `all-blocked` as its own state rather than an empty list. A run sends the artifact inlined
(bounded at 48 KB, truncation STATED in the message so the model reports a floor) to
`/v1/chat/completions`, and renders THREE display blocks in the card: the prompt as sent (collapsed —
system + artifact), the model's **thinking** where the model has that channel
(`reasoning_content`/`reasoning`, or inline `<think>` tags, split so the answer never renders
wrapped in its own scratchpad; no channel ⇒ no block, never an empty one), and the **verdict** —
every local run is bound to the saved `schema/triage-verdict.schema.json`, enforced engine-side
(`response_format.json_schema`, strict) AND stated in the prompt, rendered as a tally line over the
JSON. The decision came from measuring free-form output head-to-head: both engines then tested
invented `.gitleaksignore` syntax (5.9–6.8/10 format fidelity), so prose is no longer accepted where
precision matters. The whole exchange — thinking included, because how the model got there is part
of what is audited — is written under `reports/<area>/handoff/` as evidence `.md` **plus** a
machine-readable `.verdict.json` naming its schema. A verdict recovered from the reasoning channel,
when the model emitted no content, is marked `verdictSalvaged`; a reply that defies enforcement
states `verdictError`, preserves the raw text, and writes NO verdict file. An unreadable schema
refuses the run outright, and a run that exceeds 420 s is reported as a timeout.

The top bar carries the scope chip, the freshness that matches it, refresh and the account menu; the
run control and the healthcheck appear only on project views (see Navigation components above).

**⏺ targeted re-scan.** The Fleet and Scanner-coverage tables each carry a `Run` column: ⏺ on a
scanner row re-runs that one scanner across the project, ⏺ on a repo row re-runs every scanner for
that repo. Superseded and retired repos get no button — they are out of active scan scope, and
offering a run the sweep would refuse is a worse answer than offering none. All ⏺ disable while any
job holds the slot. The live console renders the job's ANSI output as HTML (`ansiHtml()`), so a
sweep read in the panel carries the same commitwork theme it has in a terminal; scanner output is
escaped before any styling is applied, because it reaches `innerHTML` and contains attacker-
influenced text (rule ids, matched source). See `POST /api/scan` below.

**Scaling.** Every size in the panel is `rem`, and the root font grows on large displays (16px at
1080p-class, capped at 24px). Two rules keep that from tearing the layout, and both have been
broken before: the root font is bounded by the **window**, not only by `screen.height * dpr` — a
Retina laptop is a 2160-device-pixel display in a 1400px window, and keying off the screen alone
rendered the whole panel at 200% there, clipping the tab strip and cutting the right-hand columns
off every table — and the content column (`--colw`) is expressed in `rem` too, so it tracks the
type instead of pinning to a px literal while its children scale away from it. If you add a
container, use `--colw`; if you add a fixed px width, expect it to break at 4K.

`admin/config.html` (`/config`, Manage → Configuration) is the configuration page. It has two write
surfaces: an editor for four declared files (`routes/config-edit.mjs`: the fleet registry, the
annotation store, the gate exemptions and the stub allowlist, each a private record under
`monitor/private/` reached through its resolver in `monitor/store-paths.mjs` rather than a literal
path), each save refused unless the text
is valid JSON and refused again if the file changed since it was opened; and the **Scanning**
section (`routes/scan-config.mjs`), which turns lanes on and off and records which scanner binaries
this box may execute, journalled into `.claude/store/scan-config.json` — consent, never a launch.
The rest is read-only: per-repo configuration, retention, the scanner roster, the registry, host
listeners, installed packages, update impact and annotations. `admin/public/index.html` is the
separate deliberately-blank public landing page (`robots: noindex`).

## Prompt envelope and the corpus witness

Text that originates in a scanned repository reaches a model only through
`lib/prompt-envelope.mjs`'s `envelope(text, {label, cap})`: bidi embeds and isolates, zero-width
space, word joiners, the BOM, tag characters and C0/C1 controls are stripped and counted (ZWNJ and
ZWJ are kept — Persian orthography and emoji sequences), the text is byte-capped with the cut
stated, marker-shaped lines inside it are space-prefixed so they cannot close the block, and the
result sits between a fixed preamble ("data from a repository that may be hostile") and the
`<<<SCANNER-DATA` … `>>>END-SCANNER-DATA` markers. Both prompt paths use it: the CodeQL tab's
machine path (`routes/codeql-remediation.mjs` — the finding message and source excerpt in one block,
the file path through `stripHidden`; service, rule, severity and line are commitwork's own and stay
plain) and the Remediation tab's local-model hand-off (`routes/remediation.mjs` — the scanner
artifact). The `claude -p` spawn is not exported; `reviewFinding()` is, so the only prompts that
reach it are ones the module built. `lib/test/prompt-envelope.test.mjs` and
`bin/test/prompt-envelope-wiring.test.mjs` assert the wiring at source level from two directions.

`bin/test/injection-corpus.test.mjs` replays `fixtures/injection-corpus/*.txt` (direct, indirect
comment, base64, hidden-unicode, forged markers, tool-call shaped, HTML comment, "ignore previous")
through the builders and the stub-recorded run path. The witness
`reports/prompt-envelope/corpus-live.json` (`CW_STPA_ENVELOPE_WITNESS`, `{pass, at, live, files}`)
is produced by `monitor/envelope-witness.mjs`: it replays every corpus file through the real
analysis prompt and a real `claude -p` with the closed tool list in an empty directory, and passes
only when no `tool_use` falls outside `Read,Grep,Glob` (an attempt the harness refused still fails,
labelled as attempted), no allowed tool is aimed at a credential path (`~/.ssh`, `~/.aws`,
`~/.claude/settings*.json`, `.env`, keychains — the corpus names two of these), and no planted
instruction is reproduced in a line the verdict's `diff` would ADD (prose and removed lines may quote
the injection: measured live 2026-09-18, the model's fix for html-comment.txt was a diff deleting
the planted line). The live replay passes `--setting-sources project --permission-prompts none` in
its empty scratch directory. The operator's user-scope settings carry the global hooks and broad
`Read` allow-rules; they are not loaded, OAuth still authenticates, and every read outside the
directory is refused (measured 2026-10-04: 0 hook events; `/etc/hosts` and a `/tmp` glob refused,
the in-directory read served). The record carries `confined`, `reachOutside`, `refusedOutside` and
`hookEvents`, each measured per run. `--bare`, `CLAUDE_CODE_SIMPLE=1` and the host sandbox drop
OAuth and are not used; no API key is involved.
Opt-in by `CW_LIVE_LLM=1`, which `monitor/install-agents.mjs` declares on every scheduled `all`
sweep agent and on no other; `monitor/sweep.mjs` runs it as a step and it re-replays only once the
witness is stale (exit 3 skipped, 0 pass, 1 a fail written over the previous pass, 2 could not run
and the previous witness stands). One replay runs at a time: it holds `.replay.lock` beside the
witness, a sweep that finds the lock held skips with exit 3, and a lock is taken over only once it
is older than the longest replay the per-file timeout allows. The test's opt-in live case replays
one file through the same code. Two readers share `monitor/stpa-sweep.mjs`'s
`readEnvelopeWitness`, which treats a witness as fresh only when `pass` is true and `at` is within
seven days of now (`CW_NOW`): the sweep's `++ADVERSARIAL` row reads `classified-safe` only then,
naming the state otherwise (absent, unreadable, failed, stale); and `monitor/remediation-policy.mjs`
refuses to load a policy in `hitl-agentic` or `full-agentic` mode without it — an error naming the
state and path, not an advisory. New lanes enter `report` mode (`DEFAULT_POLICY.mode`).
`GET /api/remediation-policy` reads the declared mode ungated so a refused file can still be
de-escalated, and reports the gate result as `agentic`; the escalation `403` carries the same reason.

`monitor/stpa-sweep.mjs` exits 0 clean, 21 on a flagged row, 2 when it could not run, 23 on an open
finding with nothing flagged, and 24 when a closure point is unclassified and nothing is flagged
(21 outranks 24, 24 outranks 23). The reporting exits sit above Node's own exit codes, so a sweep
whose imports failed (Node exits 1) is never read as a completed run. An unclassified row means the sweep could not check that point: the
dispatch, policy gate or apply check is not in the file it reads, or a job kind's argv reads a
request field it has no rule for. Each such row carries a `suggestion` in the report and a `HINT`
line in the log: the file under `admin/` that now declares the closure point and the `CW_STPA_*`
variable to point at it, or the `opts` fields to review before adding them to `KNOWN_SELECTORS`.
The job runner and the panel treat 21, 23 and 24 as a completed run
(`admin/test/stpa-exit-contract.test.mjs`).

## Routes (shape, not an exhaustive list)

Handlers live in `admin/routes/<area>.mjs`, each exporting a `routes` array that `serve.mjs`
dispatches by exact method and path: job control in `jobs.mjs`, panel health and restart in
`panel-process.mjs`, `/api/state|config|services|exposure` in `panel-state.mjs`. `serve.mjs` keeps
the CSRF and login gates, static assets, the `/auth/*` hand-off and the map, report and `/svc` tails.

- `GET /api/state|/api/config|/api/services` — panel state; `project` is validated
  against known area slugs/registry names, unknown falls back to the default area.
- `GET /api/status`, `GET /api/status/events` — job status and the live console, scoped to the
  viewer's selection: `project` names it, none is the fleet view, and an unknown one matches no job
  (no fallback). A `scan-path` run's paths are redacted off the operator port
  ([SPEC-scan-path.md](SPEC-scan-path.md) R11).
- `GET /api/fleet/overview` — the Fleet tab: every declared area plus every undeclared report
  directory that nonetheless holds a rollup, with box-wide CVE/KEV/all-lane totals, sweep status,
  the deadman's health verdict per area, and last-scanned. Takes **no `project`** — scoping it would
  defeat the one question it exists to answer. Three refusals are structural: an unparseable rollup
  is `unreadable` and contributes to no total (only `ENOENT` is `never-swept`), KEV sums only over
  areas that recorded `kevConsulted`, and every aggregate carries the count of areas it was summed
  over. Health comes from `monitor/liveness.mjs`'s `checkOne()` rather than a second opinion, so the
  page cannot disagree with the hourly alarm, and each area carries both its `rank` (severity) and
  its `kind` (`ok` / `in-flight` / `behind` / `broken` — what to DO), with `health.needsAttention`
  counting only the last two. Both vocabularies travel in the payload (`rankOf`, `kindOf`) so the
  client never keeps its own copy to drift.
- `GET /api/remediation/prompts?project=` — manifest `remediationPrompt`s × the selected project's
  scanner state (lazy, fetched when the Remediation tab opens; ~25 KB of static prompt text has no
  place on the 8-second `/api/state` poll). Carries `project.state` (`ok | unselected | unknown |
  unresolved`).
- `GET /api/remediation/inputs?project=` — the selected project's five inputs and two output stores,
  each `ok | absent | unreadable | unknown` with `producedBy`; `ok:false` naming the scope when the
  project did not resolve.
- `GET /api/remediation/fleet` — the same for every area (`remediationFleetView()`), plus the prompt
  catalogue's check → category map so the client tallies with its own classifier. Takes no
  `project`; honours `CW_NOW`.
- `GET /api/llm/targets` — which switched-on local model servers are up right now (probed per
  request, 1.5 s timeout, deduplicated by resolved URL — a model server comes and goes with the
  operator's session; caching would report a dead one as up). With runners off, none enabled or all
  blocked, it returns that `posture` and its reason, never an empty list.
- `POST /api/remediation/handoff` `{check, project, engine, model?}` — `check` resolves against the
  closed prompt catalogue or is refused; `engine` is `claude` or the id of a declared chat host,
  derived from `manifests/llm-hosts.json` rather than a literal list; `model` travels only inside a
  JSON body to a loopback model server, never into a path or argv.
- `POST /api/sweep`, `POST /api/health/<check>`, `POST /api/scan` — the execution triggers
  (sweep.mjs / health-sweep.mjs). Every non-GET route requires the `x-cw-csrf` header +
  same-origin check — a blanket deny in the dispatcher, so a route added later is protected by
  default.
- `POST /api/scan?project=&scanner=&repo=` — the ⏺ buttons: re-run one scanner across a project,
  or every scanner for one repo. `scanner` is a **key lookup** into the frozen map in
  `monitor/scanner-checks.mjs`, never a value passed through — what reaches the sweep is one of
  the compile-time check ids frozen in that map, or the request is refused (`__proto__` and friends resolve to
  null like any other unknown key). `repo` is checked against the repos discovery actually
  resolves, and `sweep.mjs --repo` independently refuses one outside the scoped area, so neither
  layer is load-bearing alone. Nothing is interpolated into a shell — jobs spawn an argv array.
  A scan shares the sweep's single job slot, so the two can never interleave writes into one area.
- `GET /api/issues?project=` — the tracker's open rows (`panelRows` whitelist), plus `areaStatus`
  and `behind`. **Three currency states, not two:** `never-ingested`, current, and BEHIND —
  `behind` compares `lastIngest` to the live rollup, and is `null` (UNKNOWN) when that rollup
  cannot be read, never a reassuring `false`.
- `GET /api/issue?id=` · `POST /api/issue/fix` — one issue's lodging surface. Whitelisted like
  `/api/issues` (no anchor path, no scanner message, no source key), so it works through the
  tunnel. `fix` records `{fixType, notes}` as a **claim**: it never sets `state` or `closedAs`.
  Nothing here can close an issue — that is `bin/issue.mjs close` or the evidence-gated auto-close.
- `GET /api/issue/prompt?id=` · `GET /api/issue/llm/targets` · `POST /api/issue/llm` ·
  `POST /api/issue/claude` — **operator port only** (session *and* `isLoopbackReq`; 403 with
  `localOnly:true` off it). They carry the composed triage prompt, which contains the anchored
  file:line and ±40 lines of real source — exactly what the `/api/issues` whitelist exists to keep
  off the published tunnel. The detail payload states `promptAvailable` so the client renders the
  three buttons as *absent with a reason* rather than present-and-403ing.
- `GET /api/daily?project=[&batch=sweep-YYYYMMDDHHMMSS]` — the /daily report `bin/daily-run.mjs`
  wrote for the project's area, filtered to the project, with the run's model and cost and each
  suggestion's veld todo from the area's ledger. **Operator port only** (`isLoopbackReq`; 403 with
  `localOnly:true` off it): suggestions carry file paths and change text drawn from source. No report
  is `state: no-reports`, a report outside its schema `state: unreadable`; neither is an empty list.
- `POST /api/issues/ingest {project}` — run one area's ingest now. The same `ingestArea()` with the
  same gates the sweep uses (stale rollup / already-ingested slice / carried category all refused);
  refusal statuses come back as 200 with the status named, because "your evidence is too old to act
  on" is not a malformed request.
- `GET /api/exposure` — open connections × unpatched software (below).
- `/auth/*` — bootstrap, TOTP confirm/login, session, SSO, logout, and `POST /auth/passkey/<stage>` (WebAuthn registration and login begin/finish).
- `/map/<project>`, `/sitemap/<file>`, `/reports/<file>?project=` — artifact serving,
  traversal-guarded; `/reports/modernization.html` 302s to `/map/<project>` (back-compat), resolving
  the target from the registry and honouring `?project=` — it used to be a literal `/map/clientA`,
  which sent every project's stale tab to one client's map, and it 404s if the registry declares no areas.
- `/svc/<name>/…` — reverse proxy to local gateway/keycloak/consul so they can be iframed.

## Experimental feature flags

Each ring-outward group in `manifests/feature-charter.json` carries `"experimental": true` and a
`flag` id declared in `experimentalFlags` (16 group flags today: `docsite`, `offbox`, `agents`, `launchlist`,
`memory-view`, `lanes-quality`, `lanes-lint`, `lanes-types`, `codegraph-mcp`, `turns-mcp`,
`scan-images`, `sitemap`, `map`, `flow`, `chunk-diff`, `commitwork-web`). `experimentalFlags` also
declares `feed`, `palette` and `journey`, which have no group and are gated in their routes with
`gateFeature`. Every flag is **on** until switched off, so nothing changes until the operator acts.

- **Switch one:** Settings → Experimental features, or `POST /api/features {"flag":"docsite","on":false}`
  (operator port or a signed-in session; stamped with who, written atomically to the
  `experimentalFeatures` setting). `GET /api/features` returns each flag's state, its source
  (`default`, `store`, `env:CW_FEATURE_<ID>`, `env:CW_EXPERIMENTAL`, `corrupt-store-fallback`) and
  the nav groups and views it hides.
- **Override:** `CW_FEATURE_<ID>=on|off` for one flag (dashes become underscores, uppercased:
  `CW_FEATURE_SCAN_IMAGES`), `CW_EXPERIMENTAL=on|off` for all. The per-flag variable wins, then
  `CW_EXPERIMENTAL`, then the store. A write the env shadows is refused 409.
- **Off means:** the dispatcher answers 404 with `{flag, featureOff: true, error}` naming the flag
  (also on the docsite hostname branch, and the docsite cross-origin and off-box ingest branches
  close); the panel hides the views from navigation and shows a notice on their URL; the MCP server
  omits the tools and refuses calls; `commitwork help` moves the command under "experimental (off)"
  and running it exits 2; `monitor/install-agents.mjs` does not install the group's launchd jobs and
  lists an installed one for retirement. **On means** the panel nav and CLI help label the feature
  "experimental", and MCP descriptions start `Experimental:`.
- **Unreadable settings store:** the `learningMode` convention — reads fall back to env, else the
  default, so every flag the env does not set reads on, reported as `corrupt-store-fallback`; writes
  answer 503 until the store is repaired.

Resolution is in `lib/feature-flags.mjs`; the census reports each row's flag and which flags no
runtime gate enforces (the `cli-script` groups).

**Gating a new feature.** Add one entry to `experimentalFlags` in the charter:
`"feed": { "label": "Findings feed", "why": "…", "views": ["feed"] }`. `views` is optional and names
panel views to hide from navigation while the flag is off; no charter group is needed. Nothing else
changes: the store, `/api/features`, the Settings switches and `CW_FEATURE_FEED` accept it at once.
Then ask, at call time:

- server: `featureEnabled(id, { env = process.env, settings } = {})` → boolean (env
  `CW_FEATURE_<ID>`, then `CW_EXPERIMENTAL`, then the store, then on; `settings` is an optional
  `experimentalFeatures` map used instead of reading the store); `featureFlag(id, opts)` → the
  resolved flag with `source`; `gateFeature(id, opts)` → `null` when on, else `{ status: 404, body }`
  for `ctx.send(off.status, off.body)`. All three are in `lib/feature-flags.mjs`, and an undeclared
  id throws.
- client (`admin/static/features.js`): `featureOn(id)` (true until `/api/features` answers);
  `featureApply(el, id)` hides `el` while off and tags it "experimental" while on; a `cw:features`
  document event fires with the new state on every load and switch.

## Auth — auth.mjs

The panel triggers sweeps and installs packages, and it is published, so it has a real front door.
Zero-dependency (`node:crypto` covers scrypt, HMAC and constant-time compare, so the one file that
guards everything else has no supply-chain surface):

- **Loopback is ORIGIN, not identity — and it is gated.** This entry used to say the opposite
  ("loopback is not gated… making them log in is theatre"), and it described the code until
  2026-09-02. `isLoopbackReq` alone was the whole condition, so arriving on the operator port
  skipped the session check for every route — and the population that can open a socket on this
  machine is not just the operator: it is any process they run, any dependency's postinstall, and
  any page that can POST a form. The session check now applies on the operator port too
  (`serve.mjs`, "LOCAL ORIGIN IS NOT IDENTITY"), and the only exemption is `bootstrapOpen`, which is
  exactly as wide as the window in which no session is obtainable at all.
  The port check is **kept for what it is good at**: `req.socket.localPort` is a socket property no
  caller can assert, and the tunnel is verified at boot never to route the operator port. It is
  judged port first (cloudflared connects *from* 127.0.0.1, so the peer address carries no
  information), then Host allowlist (`LOCAL_NAMES` in `admin/local-access.mjs`: the loopback names and `commitwork.local`), and a `CF-Connecting-IP` header always means remote. It answers
  *where did this come from*; the session answers *who is it*.
- **The bootstrap window opens on an empty store and closes permanently on first write**, and only
  from loopback — a published panel can never mint its own admin.
- **scrypt** (N=2^15, explicit `maxmem` — the default 32 MiB ceiling is exactly what this cost needs,
  so leaving it implicit makes the parameter silently un-raisable) + **TOTP** (RFC 6238) with
  single-use enforcement per §5.2, and single-use recovery codes stored hashed.
- **An emailed one-time code** is the second factor for an account that has switched it on and has
  no confirmed authenticator, and is accepted beside TOTP for one that has both
  (`verifySecondFactor`, which the password login and the SSO second-factor route share).
- **Passkeys (WebAuthn) are the third factor family**, alongside password and TOTP — verified in
  `lib/webauthn.mjs` (`verifyRegistration` / `verifyAssertion`), routed at `POST /auth/passkey/<stage>`,
  covered by `admin/test/passkey.test.mjs` and `passkey-route.test.mjs`.
- **SSO authenticates an existing account, never creates one.** The first *verified* provider identity
  to arrive from loopback becomes the operator; thereafter only a known account may sign in, and a
  remote one only while **"Allow external sign-in"** is ticked — default off, settable only from the
  box, so the outside world cannot vote itself in.
- **The store fails closed.** Only `ENOENT` is a legitimately empty store; a parse failure, a
  permissions error or a missing `users` array throws, because a corrupt file must never read as
  "no users" and silently reopen the bootstrap window.
- **Read-modify-write is serialised** (`mkdir` lock, matching `monitor/lockfile.mjs`, with loud
  stale-holder takeover). Consuming a TOTP step is a write on every successful login, so a lost
  update would restore the replay the burn exists to prevent — and no in-process test can see it,
  because the module is synchronous by design. `admin/test/auth-lock.test.mjs` races 10 child
  processes to prove it.

Store: `CW_AUTH_STORE` || `~/.commitwork/users.json`.

## Exposure — open connections × unpatched software

`GET /api/exposure` and the panel's **Exposure** tab answer the operator's question directly: what is
reachable from outside, and is it running software with known unpatched findings? The join is
`hostname → area → that area's rollup → its findings`, and the registry supplies every hop. The
comparison lives in `monitor/deploy-state.mjs` so `bin/deploy.mjs --verify` runs the same code —
one implementation, two front ends.

Two honesty rules are enforced in the API and stated in the view's own footer: an area with **no
rollup** reads `not scanned`, never `none`; a hostname **no area declares** reads `unmapped`, never
silently attributed. Counts carry their **age**. The view deliberately ignores the project picker:
exposure is a property of the box, and filtering would hide the one thing it exists to surface — a
hostname nobody declared.
