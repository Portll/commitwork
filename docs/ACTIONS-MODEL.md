# The GitHub Actions workflow model

commitwork reads a repository's workflow files with its own code and no runtime dependency, and
grades that code against GitHub's published parser in tests that never ship the parser. This page
says what the reader covers, how it is graded, and where it stops.

## The modules

| Module | What it does |
|---|---|
| `lib/actions-yaml.mjs` | Reads the YAML subset workflow files use into a tree of scalars, sequences and mappings, each with its line and the source text it came from. Anchors, aliases, merge keys, tags, complex keys and tab indentation are refused by name. |
| `lib/actions-expressions.mjs` | The expression language: lexer, parser and evaluator for `${{ }}`, with GitHub's comparison coercions, case-insensitive strings, object filters and the eight built-in functions. Status functions and `hashFiles` are supplied by the caller. Also the transform that turns a string with embedded expressions into one `format()` call. |
| `lib/actions-schema.mjs` | The workflow schema as data: every definition GitHub validates against and the contexts expressions may use at each site. Generated by `bin/actions-schema-gen.mjs`; see `docs/THIRD-PARTY-NOTICES.md`. |
| `lib/actions-workflow.mjs` | Validates the tree against the schema, reports what GitHub reports (unexpected keys, missing required properties, expressions where none are allowed, duplicate keys, bad identifiers), then builds the model: events with their filters and inputs, jobs with `needs` checked for unknown targets and cycles, `if` conditions wrapped with `success()` as GitHub wraps them, steps with GitHub's generated ids, and `expandMatrix` with the documented include and exclude rules. |
| `lib/actions-oracle-compare.mjs` | Compares one file's token tree and converted jobs with GitHub's parser, for the tests and the grading command. |
| `bin/actions-grade.mjs` | Grades a corpus of workflow files against the oracle and writes a JSON report. |
| `bin/lib/actions-oracle-load.mjs` | Loads the oracle from `CW_ACTIONS_ORACLE_DIR`, or says why it cannot. |

## The oracle

GitHub publishes the parser its editor tooling uses as two MIT packages, `@actions/workflow-parser`
and `@actions/expressions`. They are the oracle, in the sense cobolwork's parser is graded against
GnuCOBOL: installed outside the repository, imported only by tests and the grading command, never
by product code and never listed in `package.json`.

Install it once per machine:

```sh
mkdir -p ~/.commitwork/oracles/actions && cd ~/.commitwork/oracles/actions
npm init -y >/dev/null && npm install --no-audit --no-fund @actions/workflow-parser@0.3.61 @actions/expressions@0.3.61
```

The published build imports its schema JSON without the import attribute current Node requires, so
the installed copy needs one edit before it loads:

```sh
cd ~/.commitwork/oracles/actions/node_modules/@actions/workflow-parser/dist
sed -i '' -E 's/(from "[^"]+\.json");/\1 with { type: "json" };/' workflows/workflow-schema.js actions/action-schema.js
```

`CW_ACTIONS_ORACLE_DIR` points the tests and the grader elsewhere. When the oracle is absent the
oracle tests skip and say so; they never pass on nothing.

## How it is graded

`lib/test/actions-oracle.test.mjs` runs three comparisons when the oracle is present:

1. **Expression parity.** A battery of 661 expressions, each evaluated by both implementations
   against one context, compared on the JSON of the result or on which phase refused it.
2. **Corpus acceptance.** Every expression in every workflow file under `CW_ACTIONS_CORPUS_ROOTS`,
   parsed by both, compared on accept or reject.
3. **Workflow parity.** Whole files: both readers must agree on every validation verdict, on the
   token tree with expressions resolved, and on the converted jobs and steps.

`node bin/actions-grade.mjs --root <dir> --out report.json` runs the same comparisons over any
directory of repositories and tallies them.

As of 2026-10-07, over 3,339 workflow files from four local corpora of public repositories:

| Measure | Count |
|---|---|
| Expressions found | 50,873 |
| Expression acceptance agreements | 50,873 |
| Expression acceptance disagreements | 0 |
| Files both readers accept and model identically | 3,306 |
| Files both readers refuse | 27 |
| Files only commitwork refuses | 6 |
| Files only GitHub's parser refuses | 0 |
| Files accepted by both with a differing model | 0 |

The six files only commitwork refuses all use YAML anchors. The 27 both refuse are broken or
unsupported workflows on which the two readers agree. Three differences between the readers are set
aside by the comparison and are not counted above: GitHub's parser builds an expression inside a
block or folded scalar from the raw source lines, so it keeps indentation, folding and line endings
the decoded value does not; it wraps a multi-line condition in a `format()` call with the surrounding
whitespace; and its input-type enumeration has no `number`, so it drops that type where the model
keeps it. The corpora are local checkouts of public repositories used for other measurements:
100RandomRepos, 3185RecentCobolRepos, PHPRepos and Guests.

## Where it stops

- YAML anchors, aliases, merge keys and tags are refused with a named error. GitHub's own reader
  accepts aliases; a workflow using them is reported as unreadable here rather than misread.
- `hashFiles`, `success`, `failure`, `cancelled` and `always` evaluate only when the caller supplies
  them, because they depend on a run's state and workspace.
- Reusable workflows are modelled as a job with a `ref`; the referenced file is not fetched.
- The schema is GitHub's `workflow-v1.0` as of `@actions/workflow-parser` 0.3.61. Keys GitHub adds
  later are unexpected values until the schema module is regenerated.
- Nothing here executes a step. The model is the input to the runner, not the runner.
